# Muza Watch — brand and store assets

Everything here is generated from SVG masters, so it can be re-rendered at any
size without quality loss. Edit `src/*.svg`, then:

```bash
bash brand/build.sh
```

Needs `librsvg2-bin` and `graphicsmagick` (`apt-get install -y librsvg2-bin graphicsmagick`).

## The mark

A bold geometric **M** in white on a red tile. It was chosen over four
alternatives — including versions with a play triangle worked into the
letterform — because it is the only one that still reads at 48 px, which is the
size that actually matters on a home screen and in store search results. Icons
that carry a second idea (a play arrow, a circle) turn to mush there. The
"streaming" message is carried by the wordmark, the feature graphic and the
screenshots, where there is room for it.

| Token | Value |
| --- | --- |
| Red (primary) | `#E50914` |
| Red gradient | `#F6121D` → `#B0060F` |
| Ink / app background | `#141414` |
| Tile corner radius | 22% of width (only where you draw it yourself) |

## What is in `out/`

| File | Where it goes |
| --- | --- |
| `play-store-icon-512.png` | Play Console → Store listing → App icon |
| `app-store-icon-1024.png` | App Store Connect → App information → Icon |
| `ios-appicon-1024.png` | Xcode `AppIcon` asset (identical to the above) |
| `play-feature-graphic-1024x500.png` | Play Console → Store listing → Feature graphic (**required**) |
| `android-mipmap-*.png` | Legacy launcher icons (`mipmap-mdpi` … `mipmap-xxxhdpi`) |
| `android-adaptive-foreground-*.png` | Adaptive icon foreground layer |
| `android-adaptive-background-*.png` | Adaptive icon background layer |
| `android-notification-*.png` | Push notification icon — white silhouette; Android tints it, so a coloured icon shows as a grey square |
| `wordmark-on-dark.png` | Site header, dark listings |
| `wordmark-on-light.png` | Light backgrounds, invoices, letterheads |
| `favicon-32.png`, `apple-touch-icon-180.png` | Web |

Two constraints the build handles, both of which cause rejections if missed:

- **Apple rejects any icon containing an alpha channel.** The 1024s are
  flattened onto opaque red and stripped of alpha. Verified with
  `gm identify -format "%A"` → `false`.
- **Neither store wants rounded corners baked in.** Both apply their own mask.
  Supply the full-bleed square; rounding it yourself leaves dark corners.

## Applying the launcher icon to the app

`mobile/android/` and `mobile/ios/` are gitignored and regenerated by the build,
so icons copied into them by hand are wiped on the next build. The durable way
is `flutter_launcher_icons`, which regenerates them from a committed source
image every time. In `mobile/pubspec.yaml`:

```yaml
dev_dependencies:
  flutter_launcher_icons: ^0.14.1

flutter_launcher_icons:
  image_path: "assets/brand/icon-1024.png"
  android: true
  ios: true
  remove_alpha_ios: true
  adaptive_icon_background: "#B0060F"
  adaptive_icon_foreground: "assets/brand/icon-foreground-432.png"
```

Then `dart run flutter_launcher_icons` once, and add that command to
`muza-build-apk.sh` before `flutter build` so a regenerated `android/` folder
always gets the icons back.

## Screenshots — the part you have to capture yourself

Both stores require screenshots **of the real app**; mockups of a UI that does
not exist get rejected. You cannot generate these from here, but they are quick:

**Android** (2–8 required, 9:16 portrait, each side 320–3840 px). With the phone
plugged in and USB debugging on:

```bash
adb exec-out screencap -p > shot-1.png
```

**iOS** (required for the largest iPhone size you own). Install the TestFlight
build, take normal screenshots (side button + volume up), and AirDrop or email
them to yourself. A screenshot taken on the device is already the exact
resolution App Store Connect wants for that device's slot.

Capture these six, in this order — the first two are what people actually judge
the app on:

1. Home with the billboard and a couple of rails
2. A title page with artwork and episodes
3. The player, mid-film, controls visible
4. Search with results
5. My List
6. The subscribe screen showing Mobile Money

Plain screenshots are fine. Device frames and marketing captions are optional
and often convert no better.

## Listing copy you still need to write

- **Short description** (Play, 80 characters max)
- **Full description** (Play, 4000 max; App Store, 4000 max)
- **Privacy policy URL** — you already have <https://ham.sentepos.com/privacy>
- **Content rating questionnaire** (Play) and **age rating** (Apple)
- **Data safety form** (Play) — declare the phone number, and the payment data
  handled by Stripe/Yo

## Two things that will otherwise stall the review

**Reviewers cannot receive your SMS code.** Both stores test from their own
devices with their own numbers, and an app that can only be entered via an OTP
sent to a Ugandan handset is a guaranteed rejection ("could not sign in").
Fortunately PIN sign-in needs no SMS at all: create one ordinary account, set a
PIN on it, give it a subscription so the reviewer can reach playback, and put
the phone number and PIN in the **demo account** fields — App Store Connect →
App Review Information, and Play Console → App access → "All functionality is
restricted". Test that login yourself on a clean install first.

**Review happens against the live catalogue, before publication.** You have said
you will deactivate the copyrighted titles before going live — the thing to be
careful about is the ordering. A reviewer opens the app during review, which is
*before* anything is published, and browses whatever the API is serving at that
moment. So the catalogue has to be clean when you **submit**, not when you
publish. Rejections for third-party content are also recorded against the
developer account, and repeat flags put the whole account at risk, which is a
much more expensive problem than a delayed release. Nothing here has been
changed or deactivated — that is yours to do when you are ready.
